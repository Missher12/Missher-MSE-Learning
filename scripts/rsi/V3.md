# scripts/rsi v3 — v2 plus one guard (offline policy experiment)

Developer-only experiment. It does **not** change the runtime, UI, configuration, labels, old
evaluator or online policy. It is not installed or wired into any page/background task.

## Candidate

`v2-plus-one-guard-offline-v3`

1. Call the accepted `guardPreservingApplicabilityFirst` and keep the complete v2
   `offered`/`lines`/order/version/mode exactly as returned. Never delete, replace or shorten a v2
   entry and never redo v2 ordering.
2. If v2 already contains any guard, return v2 unchanged.
3. Otherwise use the production `rankForRecall` and `methodNeedsGuard` to scan guards that v2 did
   not offer, in original rank order. Append at most one real production guard line that fits the
   remaining 768-byte budget. No truncation, no using old repair steps, no synthetic warning.
   `packRecall` packs only that guard with the same `now`; scope/environment/retirement/exclusion/
   relevance gates come from `rankForRecall`.
4. The extra guard keeps its real id/version/`mode: "guard"`; its line and UTF-8 bytes are counted.
   Result limits: total ≤3, methods ≤2, bytes ≤768, at most one added guard. If no guard fits, the
   exact v2 selection is retained and the reason is audited (`no_unoffered_guard`,
   `guard_does_not_fit`, `already_has_guard`).

The selector receives only `entries`/`options`; it never receives or reads case id, expect,
critical, source or labels. No tuning/search/second candidate.

## Commands

```sh
node --test scripts/rsi/compare-v3.test.mjs
node scripts/rsi/compare-v3.mjs > delivery/rsi-autonomy016/v3/comparison-v3.json
```

The CLI accepts no argument / arbitrary path and reads only the two frozen public fixtures through
`loadDefaultCases()`.

## Two budgets, deliberately separate

- **Strict/original**: the unchanged `compareRecall` evaluator still uses `maxEntries=2`. A third
  offered entry is therefore `overBudget=true`; `strictPolicyDecision` can be `no_go`.
- **Experimental**: explicit audit `total<=3`, `method<=2`, `bytes<=768`, `v2PrefixPreserved`,
  `extraCount<=1`, and the added entry is a guard. This is reported separately and is never
  `deployAllowed=true` or an online-policy success.

`quality` uses the old evaluator's `hits`/`misses`/`falseOffers`/`guardMisses`; any newly introduced
miss, false offer, guard miss or guard-mode error relative to v2 is a hard experimental rejection:
`experimentalPolicyDecision=no_go_quality_regression`, with `qualityRegressions` entries
`{caseId, id, kind}`. No aggregate gain can offset it. The extra guard improves `guardMisses`
only while the strict budget remains exceeded.

## Output

`comparison-v3.json` contains baseline/v2/v3 per case, `strictPolicyDecision`,
`experimentalPolicyDecision`, `qualityRegressions`, per-group `extraEntries`/`extraBytes`/
`strictOverBudgetCases`/`experimentalViolations`/`appendedCases`/`reasons`, per-case `v2Verdict`,
`v3Audit`, and `v3Lines` including the actual guard warning text. `v2Verdict` is the real v2
report's `verdict`. `deployAllowed` and `automaticPromotion` are always `false`.

## Limits

- The 24 existing cases are a known regression set; the 10 comparison cases are manual/synthetic.
  This is not a blind test, a live replay or proof of online benefit.
- The experiment changes the count policy (2 → at most 3 total) only in this offline tool. The
  production `packRecall`/2-entry policy is untouched.
- `modelCalls=0` is a tool fact; `futureProviderCost=not_evaluated`; no provider is called.
