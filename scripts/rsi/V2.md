# scripts/rsi v2 — guard-preserving applicability-first (developer-only)

This is the second offline candidate, added for `MSE-OFFLINE-RECALL-V2-20261105`. It is a
developer-only comparison tool; it is not wired into the runtime, settings page or any background
job. It does not read the live store, call a provider, install/pack anything or write files except
stdout.

## Candidate

`guard-preserving-method-applicability-v2`

The production pipeline is reused in order:

1. `rankForRecall` produces the original ordered candidates and applies every existing scope,
   environment, exclusion, retirement and relevance gate.
2. `methodNeedsGuard` (the production predicate, imported directly) identifies guards. Guard rows
   stay at their **original ranked indices**. Only the non-guard slots are stably partitioned:
   `appMatch === true` first, then the original relative order.
3. The same `packRecall` packs the result with the same 2-entry / 768 UTF-8-byte limit and fixed
   `now=0`.
4. If that reorder changes packing and drops any guard the production baseline already offered
   (same id + version + `mode: "guard"`), the whole case returns the real baseline selection and
   records `guard_preservation_fallback` / `missingGuards`. A fallback is audit, never a gain.

No case id, expected label, critical flag, source or fixture metadata is passed into the selector.
There is no label-aware branch, no search loop and no second candidate.

## Commands

```sh
# New v2 checks only; the old v1 tests are untouched.
node --test scripts/rsi/compare-v2.test.mjs

# Write the real v2 comparison to stdout (report archive is a shell redirect).
node scripts/rsi/compare-v2.mjs > delivery/rsi-autonomy016/v2/comparison-v2.json
```

The CLI accepts no argument and no arbitrary case path; `--cases` is rejected. It reads only the
two existing public fixtures through `loadDefaultCases()`.

## Output

The JSON includes, in addition to the v1 evaluator fields:

- `candidateName`, `v2Summary`, `v1Summary`;
- per case: `baseline`, `v1`, `v2`, `v1Verdict`, `v1Changes`, `v2Audit`;
- `fallbackCases`, `fallbackAudit`, per-case `v2Audit.guardPreservationFallback`,
  `fallbackReason`, `missingGuards`.

Guard expectations still require id **and** `mode: "guard"` (using the existing v1 scoring logic
from `replay.mjs`, not a rewrite). A method/null mode is a guard miss, not a guard hit.

## Controls

`compare-v2.test.mjs` includes separate synthetic controls (not added to the 34-case fixture):

- guard in front / middle keeps its rank position while methods reorder around it;
- guard-only case remains guard;
- byte-boundary reorder that would drop a baseline-selected guard triggers the real fallback and
  is audited;
- scope/retirement/mode and the 2-entry/768-byte limits are not bypassed;
- changing the case id/label metadata does not enter the selector;
- import has no side effects; same input is deterministic.

## Limits

- The 24 existing cases are a known regression set; the 10 comparison cases are manual/synthetic.
  Nothing here is a blind test or a live production replay.
- Offline labelled-subset signal is not proof of online effectiveness; `deployAllowed` and
  `automaticPromotion` are always `false`.
- `modelCalls: 0` is a fact about this tool; `futureProviderCost` stays `not_evaluated`.
- Fallback preserves the baseline guard but can give up a candidate method improvement; each
  fallback is listed rather than hidden.
